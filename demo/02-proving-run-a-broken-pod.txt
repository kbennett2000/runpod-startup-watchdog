The case the tool exists for. A pod whose start command prints one distinctive
line and exits immediately, so Runpod restarts it and it crash-loops. Expected:
the watchdog sees the failure phrase repeat, stops the pod, and exits 4.

The image is alpine:3.20, the same one runpodctl's own source names when it
describes verifying port behaviour against production.

Two corrections to the notes above, written after reading the output rather
than before it. Both were wrong.

1. "so the count is checkable" — it is not, from that dump. Every event in it
   has source `system`. The three container lines the watchdog counted are gone
   from the log tail, because stopping the pod removed the container ("remove
   container" is the last system line). The container's output is readable while
   the pod is alive and not afterwards. The watchdog's own printed line, "failure
   phrase: 3 of 2", taken at 16:55:11 while the pod was still running, is the
   record of what it saw. A later reader cannot re-derive it from the log.

   What the dump does show is the crash loop itself: "start container for
   alpine:3.20: begin" appears twice in 13 lines, for one pod that was asked to
   start once. That is the restart behaviour the failure signal is built on.

2. "cost drops to 0.0 per hour" — it does not. The pod is EXITED and `cost` still
   reads 0.06. Runpod's OpenAPI document describes the field as "Current cost in
   USD per hour (0.0 when EXITED or TERMINATED)". Live, on a stopped pod, it does
   not do that. So `cost` cannot be used to tell whether a pod is still billing,
   and nothing in this tool reads it for that purpose. Recorded in ADR-0005.
